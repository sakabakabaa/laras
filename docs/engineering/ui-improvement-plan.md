# LARAS UI audit and proposed improvement plan

Captured 13 October 2026 from https://laras.zulficar.me using lecturer and mahasiswa accounts. No source changes, grading edits, submissions, password resets, or deployments were made. This is a proposed plan for review.

## Coverage and limits

The gallery covers public pages, both login roles and onboarding guides, lecturer main navigation, all linked JR242 course sections, seven lecturer assignment details, assignment creation, file context, student dashboard/practice/course sections, seven student assignment workspaces, analytics, and both account settings views. Student profile and file-context record layouts use representative records rather than duplicating hundreds of instances. File downloads/API endpoints are excluded. Screenshots show browser-rendered viewport states; long pages and nested scroll areas may extend below the captured view. Additional homepage sections are included separately.

The localhost:3000 preview could not be inspected because the browser URL policy rejected access. Findings below are from the live site. Mobile layouts and keyboard-only workflows remain to be audited before implementation.

## Proposed order

| Priority | Work | Evidence | Proposed outcome and verification |
|---|---|---|---|
| P1 | Reconcile grading status and counts | Lecturer dashboard shows **416** awaiting grading while the task list shows **417 collected, 0 awaiting**. Dashboard rows show both “68 Menunggu” and “68/68 Dinilai”. Student analytics reports 0/2 graded. | Trace submitted, AI-reviewed, draft-scored, officially graded, and published states. Use one shared definition for every count and label. Cross-check the same submissions across dashboard, task list, grading detail, gradebook, and student view. Never change grades just to resolve presentation. |
| P1 | Make student analytics actions role-appropriate | Student analytics says “1 mahasiswa belum mengumpulkan” and “Lihat mahasiswa”; that link returns the student to the course overview. It also offers “Lihat penilaian” and class-oriented headings. | Use “You have not submitted…” and links to the student's task or own grades. Keep class statistics and roster actions in lecturer views. Verify permission guards separately from wording; these captures do not establish a data exposure. |
| P1 | Repair dark-theme contrast and document surfaces | RPS/syllabus cards are pale against the dark workspace, with faint text. Some task revision/document containers show large white bands. | Audit shared card, rich-text, embedded-document, input, border, and badge styles. Define paired foreground/background tokens, keep intentional document previews readable, and check light/dark contrast. Use consistent surfaces instead of isolated overrides. |
| P2 | Complete localization and define immersion behavior | Student navigation is German, but practice pages, settings, AI assistance, editor labels, and analytics still contain Indonesian and English. Lecturer login still labels its identifier “NIM atau Alamat Email UPI”. | Separate learning-content language, interface language, and explanation language. Translate all interface messages for the selected locale while preserving original course content. Update role-specific login labels. Validate German, Indonesian, and English across both roles. |
| P2 | Clarify assignment and revision workflows | Student workspaces can show “Revisi — Jawaban asal belum ditemukan” above an unsubmitted task. Completed task views and editor views use markedly different layouts. | Show revision context only when a source submission exists. Make draft, submitted, returned, and published-feedback states explicit. Keep task instructions, response, AI help, and submission controls in a predictable order. Check each existing state using read-only samples before changing behavior. |
| P2 | Improve lecturer navigation and dashboard hierarchy | The workspace has global and course navigation; Tugas, Penilaian/Nilai, Berkas, and Analitik appear at multiple scopes. The dashboard gives a large area to the AI composer. | Clarify global versus course scope, add consistent breadcrumbs and page headers, and preserve course context between tasks/grades/files. Prioritize actionable teaching work and place AI assistance where it supports the current task. Verify common paths with both expanded and collapsed sidebars. |
| P2 | Make long tables, documents, and file libraries easier to scan | Roster has 72 students; course files have hundreds of records; task grading uses a dense three-column workspace; RPS and syllabus are lengthy. | Add or refine sticky headings, search/filter placement, pagination or virtualization where warranted, readable text size, restrained metadata, and progressive disclosure. Test long names, long German titles, empty results, and large record counts. |
| P2 | Improve loading, empty, and failure states | Files/analytics load asynchronously; account settings show “Gagal memuat penggunaan AI.” Empty practice/analytics areas provide limited next-step direction. | Distinguish loading, no data, missing configuration, and failed requests. Add retry where safe and explain the next useful action. Preserve layout while loading; do not show zero as a substitute for unavailable data. Verify with slow responses and simulated failures in a development environment. |
| P3 | Polish public entry and onboarding | Public landing page and login use a different visual treatment from authenticated dark views; onboarding video appears again on repeated sign-ins unless dismissed persistently by the user. | Align typography and core components, make entry actions clear for each role, and review first-visit versus returning-user onboarding. Preserve the user's onboarding choice and offer the guide from Help. |
| Validation | Responsive and accessibility pass | Current captures are desktop viewport states only. | Before shipping, inspect 390 px mobile, 768 px tablet, and typical desktop widths; keyboard navigation, focus visibility, dialogs, tab order, error announcements, reduced motion, and contrast. Verify both roles and locales against the captured baseline. |

## Implementation batches after approval

1. **Status accuracy and role-specific analytics.** Establish the grading-state model, fix labels/actions, and add focused regression checks for counts and access guards.
2. **Shared theme and localization foundations.** Fix component tokens and interface strings before individual page redesigns.
3. **Assignment and grading workflow.** Clarify revision context, editor structure, feedback, and submission status.
4. **Dashboard, navigation, and dense data screens.** Improve hierarchy, course scope, table/file browsing, and loading/error states.
5. **Public pages, onboarding, and final verification.** Complete responsive/accessibility checks and compare before/after screenshots.

Approve or adjust these batches before source changes begin. Repository identification and local-preview verification are still needed for implementation.
