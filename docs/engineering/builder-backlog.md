## Editor layout locks (2026-11-06, implementation contract)

`layoutLocked?: boolean` on blocks and SECTION/CONTAINER groups defaults to false when absent. It is editor-only accidental structural movement protection, never student access control, assessment policy, authorization or security. Ordinary content/style editing and student rendering remain unchanged.

The shared workspace mutation boundary checks the previous document before accepting any edit: a locked node and every descendant retain their activity, ancestor chain, sibling position, identity, kind and subtree structure. Thus moving/reparenting/reordering/deleting a protected node, moving/deleting its ancestor or activity, and destructive proposal REPLACE/template application are rejected. Unlock-and-delete in one mutation cannot bypass the previous lock. Add/move destinations inside a locked group are rejected, including appending: the complete protected subtree structure is fixed. Conservatively, insertion/removal/reorder before a protected sibling (including activities) is also rejected because it changes its position; changes after it or in unrelated unlocked branches are allowed if no protected position changes. Rejection explains that the relevant lock must be removed first.

Unlock is always selectable independently of structural controls; inherited protection is distinguished from the node's own toggle and requires unlocking the named ancestor. Toggles use the existing single undo/redo change and honor conflict, recovery, read-only and backend capability guards. Undo/redo intentionally restores whole prior states, including locks; it is not an authorization bypass. Duplication generates independent IDs/keys and removes all own/inherited source lock flags in the copy; insertion must still pass the same destination/position policy, so duplication inside a locked group is refused. Templates preserve source flags until instantiated through the existing duplication path.

The PocketBase draft response explicitly advertises `layoutLocks: true`; missing/false support disables toggles and refuses mutation/save/recovery of flag-bearing drafts to avoid silent field loss through an older normalizer. Flag-bearing create/save requests additionally use versioned `layoutLocks:create` / `layoutLocks:save` actions, including explicit false flags. Snapshot/template writes always use versioned actions because their source document is loaded server-side. Pre-lock servers reject these unknown commands before normalization or persistence, even if an editor remains open across rollback; this does not rely on a stale read handshake. Lock-free create/save and recovery reads retain their legacy actions. Snapshot/template writes intentionally fail closed on older backends. Server normalization accepts only boolean flags, preserves explicit false and true, and leaves legacy absent fields absent. Server code does not enforce editor lock policy as an authorization rule.

Rollback review fix validation: 62 focused lock/save/capability tests pass, including transport rejection with local draft retained, true/false flag routing, versioned save dispatch and revision-conflict preservation. Direct VM execution of the actual pre-lock `e695f0a` service rejects all four versioned commands before persistence. This is local handler/transport evidence, not browser or live rollback acceptance.
